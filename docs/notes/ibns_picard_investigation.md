## TL;DR

Two layers of finding.

**Layer 1 — about the iBns Picard.** Virtual casing is clean and the
sign convention is correct. The Picard non-contractivity at "fresh from
fix2free" geometries is itself a consequence of `iBns = 0` being far
from the iBns fixed point — far from the fixed point the map's
spectral radius is ~ 1.8; *at* the fixed point it's ~ 0.4. **Damped
Picard (`gBnbld = 0.5`) reliably converges iBns from any starting
state** (factor of ~ 4×10⁵ reduction in 15 iterations on the NCSX
3-vol test). Once iBns is at the fixed point, even undamped Picard
contracts (per-iter ratio ~ 8e-5). So: ship damped Picard in
`update_bns`.

**Layer 2 — about the "bonkers" initial force.** Updating iBns alone
**does not** reduce the initial force (it stays at `~ 10^12` per
interface before and after damped Picard converges). So `iBns = 0` is
*not* the dominant source of the initial residual; H1 from the
hypothesis list is partially wrong. The dominant source is some
combination of H2 / H3 / H4 / H5 (the dpflux/dtflux Newton residuals,
the interior interface placement from VMEC, the pressure profile, the
modal truncation). Stage 1a's first lstsq step with that `~ 10^12`
residual is so large that the interface DOFs immediately land in
intersection (force_real returns the `1e+10` overlap sentinel and the
optimizer stalls there). The user's pre-existing optimization workflow
quietly recovers from this on small problems by trust-region rejection;
on this test case it doesn't.

The investigation has separated two issues that were entangled in the
original symptoms: (a) iBns convergence, which is fixable cleanly by
damped Picard, and (b) initial-state quality, which requires either a
better starting state (smaller pressure, better interior interface
guess, more dforce warmup before letting lstsq move geometry) or
step-size control inside the optimizer.

## Problem statement

In free-boundary MRxMHD, the self-consistent `iBns` (B·n at the
plasma-vacuum interface from the plasma's contribution) satisfies:

```
iBns* = ofmn(plasma equilibrium given iBns*)
```

with `ofmn` from `compute_bnorm_plasmab` (virtual casing of plasma
surface currents). The fixed-point iteration:

```
iBns_{n+1} := gBnbld · iBns_n + (1 − gBnbld) · ofmn_n
```

with `gBnbld ∈ [0, 1]`: 0 = full replacement, 1 = freeze. The user
observed both convergence (`bnserr ~ 1e-17`) at past geometries *and*
divergence at current ones. What governs convergence?

## Finding 2 — Sign-flip hypothesis is wrong

User asked: "does the code expect the BC to be exactly negative for the
update to be self-consistent?" Direct test
(`scripts/diagnostic/picard_sign_convention.py`):

1. Run `update_bnorm` to get `ofmn1`. With `gBnbld=0`, `iBns := ofmn1`.
2. Manually overwrite `iBns := -ofmn1`. Resolve Beltrami, compute fresh
   `ofmn3`.
3. If the "should be negative" hypothesis is right, `ofmn3 ≈ +ofmn1`
   (a self-consistent state where `iBns + ofmn = 0`).

Result:
```
max|ofmn3 - ofmn1| = 3.30e+03
max|ofmn3 + ofmn1| = 1.11e+04
```

Neither close to zero. The map is not "off by a sign" — it's
non-contractive. Hypothesis **rejected**.

### Interpretation

At `gBnbld = 0` (full replacement):

- **W7-X diverges** (geometric, ratio ~ 1.8× per iter — spectral radius ~ 1.8).
- **NCSX is at the borderline of a 2-cycle** (~3000 each iter — spectral
  radius ~ 1 with a slight bias).

Damping `gBnbld = 0.5` is the sweet spot for both:

- **W7-X**: 121× reduction in 6 iterations (ratio per iter ~ 0.45)
- **NCSX**: 184× reduction (ratio per iter ~ 0.4)

Outside [0.3, 0.7], either too little damping (still divergent for
W7-X) or too much (asymptotic convergence to a non-zero limit — the
`gBnbld=0.95` row has each step ~ 91% of the previous, never reaching
zero in finite iterations).

Both geometries are happy at `gBnbld=0.5`. The optimal `gBnbld` depends
on the spectral radius `ρ` of the undamped map: convergence requires
`|1 − (1−gBnbld)·ρ_eig| < 1` for every eigenvalue. The best fixed
`gBnbld` is `1 − 1/ρ` for the dominant eigenvalue; both geometries
land near 0.5 because `ρ ≈ 2` for each.

## Connecting back to the user's past `bnserr ~ 1e-17`

At the user's past geometries (where they saw `bnserr ~ 1e-17` after
`xspech.run()`), the spectral radius of the Picard map was apparently
< 1 — geometry-dependent — so even *no damping* was contractive, and
one `LautoinitBn` step landed near the fixed point. At the test
geometries here, `ρ ≈ 2`, so the undamped map *cannot* converge no
matter how clean vcasing is. This is consistent with all the evidence
the user pointed at: convergence in some cases, divergence in others,
without anything obviously different in the inputs.

## Why this matters for `SPECTRE.update_bns`

The single-shot `update_bns` *forces* `gBnbld=0` inside (mirroring
xspech's `LautoinitBn` block). That's safe when `ρ < 1` (the
LautoinitBn-style cases) but produces an `iBns` arbitrarily far from
the fixed point when `ρ > 1` — the case shown here. Then downstream
the vol-Mvol Beltrami uses this bad `iBns` as a Dirichlet BC and
diverges.

## Recommended fix

**Don't force `gBnbld=0` in `update_bns`. Iterate damped Picard.**

Concretely:

1. Add `picard_damping: float = 0.5` to `update_bns` (the new `gBnbld`
   used during the iBns refresh, default 0.5).
2. Iterate the Picard step until `|delta iBns| < tol_ibns` *or* until
   the residual grows (safety guard).
3. Restore the user's TOML `gBnbld` on exit so the optimizer's own
   `update_bnorm` calls during minimization respect their setting.
4. Expose `picard_damping` and a `picard_max_iter` in
   `MinimizationParameters`; pass through in `Force_Minimizer`.

Default `picard_damping=0.5` looks robust across both geometries
tested; geometries with `ρ < 1` will converge in one or two iters
either way. Users with pathological cases can dial it down.

The previously-drafted **mode-filter** plan can be shelved — it would
only help if vcasing were the source of noise, which it isn't here.

## Recommended `update_bns` algorithm

```
def update_bns(self, picard_damping=0.5,
               picard_max_iter=20, tol_ibns=None, ...):
    if tol_ibns is None:
        tol_ibns = float(self.input_list_mod.gbntol)
    gbnbld_saved = float(self.input_list_mod.gbnbld)
    try:
        self.input_list_mod.gbnbld = float(picard_damping)
        prev_delta = float("inf")
        for it in range(picard_max_iter):
            self.forces_mod.dforce(...)
            before = self.allglobal_mod.ibns.copy()
            self.wrapper_funcs_mod.update_bnorm()
            delta = float(np.max(np.abs(self.allglobal_mod.ibns - before)))
            if verbose: print(f"update_bns iter {it}: |delta| = {delta:.3e}")
            if delta < tol_ibns:
                break
            # Safety: if damping isn't enough and the map is still
            # not contractive, bail rather than amplifying.
            if it > 0 and delta > prev_delta:
                if verbose: print("  delta grew — bailing")
                break
            prev_delta = delta
        # final dtflux Newton at the converged iBns
        for _ in range(max_inner):
            ...
    finally:
        self.input_list_mod.gbnbld = gbnbld_saved
```

(Sketch — the actual implementation should also keep the existing
`refresh_ibns=False` and `_sync_tflux_pflux_from_dt_dp()` paths.)

## Finding 5 — once iBns is at its fixed point, the Picard becomes contractive at gbnbld=0

A follow-up experiment
(`scripts/diagnostic/force_evolution_with_update_bns_first.py`) ran 15
damped Picard iterations (`gBnbld=0.5`) at the initial geometry,
driving `max|delta iBns|` from `2.0e+03` down to `5.4e-03` (factor of
4×10⁵). Then re-ran the contractivity test:

```
SNAPSHOT: 005_after_damped_picard   (geometry unchanged, iBns near fixed point)
  iface 0: rms = 1.497e+12  max = 2.267e+12      ← force unchanged from initial
  iface 1: rms = 2.520e+12  max = 4.220e+12
  iface 2: rms = 2.446e+12  max = 4.500e+12
  Picard:  gbnbld=0.0  CONTRACT   [4.78e-03 5.87e-04 8.05e-05 1.23e-05 2.09e-06 3.85e-07]  ratio = 8e-5
           gbnbld=0.5  CONTRACT   [2.39e-03 1.13e-03 5.31e-04 2.49e-04 1.16e-04 5.44e-05]  ratio = 2.3e-2
```

**Two huge structural findings**:

1. **Picard non-contractivity at init is itself a consequence of being
   far from the iBns fixed point** — not an inherent property of the
   map at this geometry. From the fixed point, the Picard spectral
   radius is `~ 0.4` (per-iter ratio at `gbnbld=0`); pre-damped, it
   was `~ 1.8`. The map *linearizes* nicely around its fixed point;
   far away, it's wildly nonlinear.

2. **Updating iBns alone does NOT fix the bonkers force**. The
   per-interface RMS forces after 15 damped Picard iterations are
   essentially byte-equal to the initial values
   (`1.497e+12, 2.520e+12, 2.446e+12` vs initial
   `1.497e+12, 2.520e+12, 2.447e+12`). So `iBns = 0` is *not* the
   primary source of the `10^12` residual.

**That means H1 (iBns=0 mismatch) is wrong as the root cause** of the
bonkers force. The plasma-vac boundary sign-flip in the heatmap is
real, but it's small relative to the dominant signal. The dominant
signal must come from H2/H3/H4 (`dpflux/dtflux/pressure`
mismatches) or H5/H6 (modal truncation / axis), and those are *not*
fixed by the iBns Picard.

This recasts the practical workflow:

```
1. Build from fix2free  (force ~ 10^12, iBns = 0)
2. Damped Picard (gBnbld=0.5) until iBns at fixed point  — does NOT
   reduce force; just gets iBns out of the way.
3. From here, undamped Picard (gBnbld=0) is contractive (factor 8e-5
   per 6 iters) — so subsequent iBns refreshes during optimization
   are safe at gBnbld=0.
4. The bonkers force REMAINS ~ 10^12 from sources other than iBns.
   Stage 1a/1b with this residual magnitude blows up the geometry
   (interface intersection). Need a different starting-state cure
   for the dominant residual — probably damping-or-step-control
   inside the lstsq, or a higher-quality `interface_guess`, or
   weaker initial pressure.
```

The user's instinct — "update bns after stage 1a/1b" — was directionally
right ("after we get close, the Picard converges") but the data shows
it can be done from the start *with damping*, which is cheaper and
makes subsequent optimizer steps see a state where future iBns
refreshes are stable.

## Finding 4 — initial force IS bonkers, and stage 1a's first step breaks geometry

`scripts/diagnostic/force_evolution_picard.py` builds the NCSX 3-vol
pressure case, evaluates `force_real` per interface, then runs stage 1a
(4 iters, fmodes, x_scale=1.0) and stage 1b. Output:

```
SNAPSHOT: 00_initial
  iface 0: rms = 1.497e+12  max = 2.267e+12
  iface 1: rms = 2.520e+12  max = 4.220e+12
  iface 2: rms = 2.447e+12  max = 4.500e+12   ← plasma-vac boundary
  Picard:  gbnbld=0.0    flat       ratio = 0.839
           gbnbld=0.5  CONTRACT     ratio = 0.005   (200× shrink in 6 iter)
```

The force is **`~10^12`** at every interior interface — confirming the
"bonkers" observation. Two structural features of the
`force_00_initial.png` heatmap stand out:

- All three interfaces show clear `nfp=3` periodicity in ζ — these are
  *physical* features (the field is symmetric under 2π/nfp), not noise.
- **`iface 0` and `iface 1` are positive (red); `iface 2` (the plasma-vac
  boundary) is negative (blue)** with similar magnitude. The sign flip
  is exactly the H1 signature: at interior interfaces the B² jump points
  one way (plasma's natural surface currents), at the plasma-vac
  boundary it points the *other* way (because the vacuum-side B²
  derives from `iVns + iBns = iVns + 0 = iVns`, which is set from
  Biot-Savart of coils only, missing the plasma's contribution).

Even at this terrible state, **damped Picard (`gbnbld=0.5`) still
contracts**: factor of 200 reduction in 6 iterations. The
fixed-point map is well-conditioned in the damping basin even when
the *geometry* is wildly off-equilibrium.

After stage 1a (4 iters fmodes x_scale=1.0):

```
SNAPSHOT: 01_after_stage1a
  iface 0: rms = 1.000e+10  max = 1.000e+10
  iface 1: rms = 1.000e+10  max = 1.000e+10
  iface 2: rms = 1.000e+10  max = 1.000e+10
  Picard:  gbnbld=0.0  DIVERGE    ratio = 1.0e+9
           gbnbld=0.5  DIVERGE    ratio = 3.7e+7
```

`1.000e+10` is exact-equal across all three interfaces — that's the
`force_real`'s intersection-overlap sentinel (`force_targets.py:264`).
The optimizer has pushed the interfaces into intersection. Picard then
diverges catastrophically.

**This is a critical secondary finding**: starting the optimizer from
the bonkers-force initial state is fundamentally unsafe at the
default settings. The gradient step magnitude is set by the residual
magnitude; with residual `~10^12` the trust-region step is enormous,
and the interface DOFs land in intersection. The Levenberg-Marquardt
trust-region reduction *might* recover this on later iterations, but
the optimizer's intermediate state is broken in the meantime.

**The user's intuition was directionally right** ("update bns after
relaxation") but the experiment shows the opposite ordering is what
actually works: **damped Picard at the initial state is contractive
and produces a usable iBns**, while attempting to relax the geometry
*first* (with iBns=0 frozen) doesn't actually relax — it intersects
the interfaces.

The correct order, in light of the data, is:

```
1. Construct from fix2free  (force ~ 10^12, iBns = 0)
2. update_bns(picard_damping=0.5) — Picard contracts here, gives usable iBns
3. Stage 1a (fmodes, x_scale=1.0) — now safe because force is moderate
4. update_bns again if needed  (Picard should still contract — to verify)
5. Stage 1b (fmodes, x_scale='jac')
6. Stage 2 (freal)
```

## Initial force "bonkers-ness" — hypotheses

The user has noticed that the force on the plasma boundary is always
huge at the just-instantiated state, and asks if that's connected to
the Picard non-contractivity. Plausible mechanisms (not mutually
exclusive):

### H1 — `iBns` starts at zero, plasma is not vacuum

`fix2free` writes `Bns = 0` because it can't know the plasma's
contribution to B·n at the boundary without running vcasing on a
converged Beltrami. So at preset time:

- vacuum-side B·n at the boundary = `iVns` (from Biot-Savart of coils),
  no plasma contribution.
- plasma-side B·n at the boundary = whatever the plasma Beltrami
  produces given the VMEC-interpolated interior interfaces.

These two are generically *very* different. The mismatch shows up as a
huge B² jump at the plasma boundary, which is exactly the force.

This is the leading candidate. With pressure ≠ 0, no equilibrium has
`iBns = 0` — the plasma must respond to the vacuum field. So the
"initial state" is fundamentally not an equilibrium and forcing it
into one via the optimizer with `gBnbld=1` (frozen iBns) is asking the
geometry to compensate for a missing physical degree of freedom.

### H2 — `dpflux` / `dtflux(Mvol)` at TOML guesses, not Newton-converged

`preset_mod.initialize_internal_arrays` derives `dpflux/dtflux` from
the (cumulative-normalized) TOML `pflux/tflux`. The TOML's `pflux`
comes from VMEC's nested-surface flux structure, which is *continuous*;
SPECTRE wants *discrete* surface-current jumps at each interface that
satisfy `IPDt(vvol) − Isurf(vvol) = 0`. These constraints are only
satisfied after `dfp100`'s Newton iteration. **Before** that first
Newton step, each interface has a mismatched tangential-B jump → big
tangential force. (One `dforce` reduces this; many converge it.)

Same story for the curpol constraint on `dtflux(Mvol)`.

### H3 — Interior interfaces interpolated from VMEC, not at the
equilibrium loci

`fix2free(..., interface_guess="wout")` puts interior interfaces at
the VMEC-computed nested-surface positions. VMEC's surfaces are loci
of constant ψ; SPECTRE's interfaces are stepped-pressure interfaces
whose loci depend on its own equilibrium. These can differ — and the
initial Beltrami on each side of an interior interface doesn't
automatically match across the discontinuity.

### H4 — Pressure jumps not yet balanced by field jumps

The MHD force balance at each interface is

```
[B²/2 + p]_vol- → vol+ = 0  (tangential)
```

The TOML pressure gives a jump of `Δp ~ 0.06` between adjacent
volumes (our 0.1 → 0.034 → 0.001 profile). The B² jump matching this
requires specific `dpflux`/`dtflux` values *and* specific interior
interface shapes. At preset time, neither is satisfied. The residual
mismatch is the force.

### H5 — Modal-resolution truncation aliasing

VMEC computes its solution at high modes (often mpol ≥ 12). The
`simsvmec2spectre` converter truncates the boundary and interior to
SPECTRE's mpol/ntor (e.g. 4/3). High-mode content of the VMEC solution
gets lost or aliased into low modes. The resulting initial state is a
low-mode approximation of a high-mode field — internally inconsistent,
gives residual surface currents and hence force.

### H6 — Magnetic axis re-computation

VMEC and SPECTRE may compute the magnetic axis from slightly different
criteria, and `packxi(..., 'U', .true.)` updates the axis at every
`dforce`. The first time the axis moves, the interior coordinate
transform shifts — which makes the previously-computed Beltrami
slightly inconsistent with the new metrics.

### Why this matters for the Picard

The "bonkers" force at init = the plasma is far from any consistent
equilibrium state for the given (geometry, iBns=0). When we try the
Picard map `iBns ↦ ofmn(plasma)` at this state, `ofmn` is computed
from a wildly-inconsistent plasma solution and varies discontinuously
with iBns. That gives a high spectral radius — the divergence we saw.

**Conjecture (being tested by `scripts/diagnostic/force_evolution_picard.py`):**
once the optimizer has driven the geometry into the basin of a real
equilibrium (after stage 1a + 1b), the plasma's response to changes in
iBns becomes smooth and small. The Picard map spectral radius drops
below 1. Then a single un-damped Picard step *would* land at the fixed
point — matching the user's past `1e-17 bnserr` observation.

If the conjecture holds, the recommended workflow is:

```
1. Build SPECTRE from fix2free  (iBns = 0, force is bonkers)
2. Stage 1a + 1b — fmodes optimization with frozen iBns
   (drives geometry into the equilibrium basin)
3. update_bns NOW — Picard is contractive here; converges in 1-2 iters
4. Stage 2 — freal optimization with the now-correct iBns
5. Optionally update_bns again between iterations
```

instead of the current

```
1. Build SPECTRE from fix2free
2. update_bns (Picard diverges; iBns ends up at noise)
3. Stage 1a, 1b, 2 with frozen-but-bad iBns
```

## Open questions / further tests

These would strengthen the picture but aren't required to ship the fix.

1. **What is `ρ` for the user's actual failing case?** If it's > 2,
   even `gBnbld=0.5` isn't enough — adaptive damping or Anderson
   acceleration would be needed. The damping sweep script can run on
   any TOML; the user can run it against their case.

2. **Sign-flip variants × damping**: does flipping the sign of `phiedge`
   or `curpol` change `ρ`? (The full
   `scripts/diagnostic/picard_full_sweep.py` was designed for this but
   times out on the larger W7-X mpol; if the user wants this, run with
   mpol=4, ntor=3 on both geometries.)

3. **Does `xspech` with `mfreeits > 0`** converge on these test cases?
   That would tell us whether xspech's outer free-boundary loop is
   subject to the same instability we're seeing, and whether the
   `gBnbld` from the TOML (typically `0.666` or `1.0`) is enough.

4. **Anderson acceleration** could converge faster than fixed-`gBnbld`
   damping and adapt to the geometry. Worth considering if 0.5
   isn't enough at some user case.

## Final recommendation set

Concrete changes to ship in `SPECTRE.update_bns` and `Force_Minimizer`:

1. **Damped Picard with iBns-convergence check, not single-shot**:

   ```
   gbnbld := damping (default 0.5)
   for iter in range(max_iter):
       dforce  # settle Beltrami at current iBns
       capture iBns_before
       update_bnorm  # damped: iBns := damping·iBns + (1-damping)·ofmn
       delta = max|iBns_after - iBns_before|
       if delta < gbntol: break
       if iter > 0 and delta > prev_delta: bail (non-contractive — shouldn't
                                                 happen at gbnbld=0.5)
   final dtflux Newton sweep at converged iBns
   sync tflux/pflux
   ```

   This converts the existing single-shot `update_bns` from "one
   refresh, hope it works" to "iterate with damping until iBns stops
   moving."

2. **Optionally switch to gbnbld=0 once close to fixed point.** Once
   the iBns delta is small (say < 10 × gbntol), drop damping to 0 for
   the final iterations — gives faster (geometric) convergence as we
   saw post-damping. (Equivalent to a momentum schedule.) Probably not
   worth the complexity; fixed `gBnbld=0.5` converges in ~15 iters on
   the test case which is fine.

3. **For the "bonkers initial force" — a separate issue**. Mitigations
   the optimizer wrap could take:
   - **Force a few `dforce` warmup calls** before lstsq runs, so
     `dpflux/dtflux` Newton is converged at the TOML pressure profile.
     (This costs only a few extra Beltrami solves and might bring the
     residual down significantly before the first geometry step.)
   - **Cap the first lstsq step size** when the residual magnitude
     exceeds a threshold. Prevents the immediate intersection.
   - **Document** that `fix2free(interface_guess="wout")` is a coarse
     starting state. Users should consider alternative interior
     interface guesses (e.g. `map2disc`, or a previously-converged
     run's geometry) for difficult cases.
